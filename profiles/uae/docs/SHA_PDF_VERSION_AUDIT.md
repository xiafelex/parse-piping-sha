# SHA与原设计PDF版本核验及首轮修正

核验日期：2026-10-02。对象是NativeFiles中的四份主SHA与对应`_0.pdf`；0537、0666的`_XX.pdf`没有对应主SHA，不纳入同名配对。

## 结论

四组均有强证据支持同一设计发布版本、同一次模型提取结果，可以用原PDF作为解析校验基准。不是仅凭文件名、文件修改时间判断。
这不证明所有签字、颜色、后期二维编辑完全相同，不应把每一处视觉差异直接认定为解码错误。

| 管线 | SHA与PDF共同版次/日期/状态 | 共同提取时间 | 最新绘制/校核/批准 |
|---|---|---|---|
| 0212 | 0 / 28-AUG-2026 / IFC | 2026-08-27 12:52:09 | ND / SWK / NN |
| 0937 | 0 / 28-AUG-2026 / IFC | 2026-08-26 11:46:07 | KKI / THO / NN |
| 0939 | 0 / 28-AUG-2026 / IFC | 2026-08-26 10:55:49 | KKI / THO / NN |
| 0511 | 0 / 28-AUG-2026 / IFC | 2026-08-26 03:45:08 | DT / SWK / NN |

证据：SHA的TaggedTxtData/TitleArea给出图号；TaggedTxtData/Revision给出A及0两条修订；PDF图号一致，物理修订栏内能核对上述字段及历史A版08-MAY-2026/IFI；四个PDF提取时间均在对应SHA Sheet6以UTF-16LE原文出现，精确到秒。
SHA内部MajorRev_ForRevise=2是修订记录字段，图面显示的版次来自MinorRev_ForRevise=0，不能误判为Rev.2。
PDF的创建/修改日期与提取日期是不同概念：本批PDF修改日期为8月30日，不能据此判断为另一个设计版次。
0212/0511的PDF元数据标题直接指向同名SHA；0937/0939采用生成过程中的GUID标题，不将标题差异作为版本差异。

## 第十一轮：原生字宽比例

由此定位图框8条细线：它们引用的是0x30复合图形样式39/84，而非原先仅读取的0x2E线样式。0x30的+44为颜色，+48为显式线宽；本批标志25声明0.35mm，标志1线宽为零时使用文档默认线样式1。现在这8条线均为原生0.35mm，而非缺省0.15mm；原PDF约0.339mm。目前所有图框直线均能解析到样式，不再触发默认值。

第十轮新增文字边框在0937/0939主图说明框上暴露了锚点差异：其alignment_flags=1为顶部锚点，不应套用材料表标题alignment_flags=0的基线偏移。纠正后消除约5.3mm向上偏移，说明框四条边进入端点匹配。

四份分别匹配277、174、186、222条参考直线，均无线宽差超阈值；每图剩余3条未匹配直线位于Wood字标，其SHA输出为填充轮廓，不能据此判定漏画。该工具尚不比较填充轮廓与描边轮廓的等价性。18项回归检查通过，四份PDF重新生成。

## 第十三轮：Wood原生描边

进一步检查嵌入JSite73756/PSMcluster0，确认除了已恢复的5个0x13填充轮廓，还存在3条0x18直线、6个0x59圆、1条0x61圆弧和1条0x84折线。这11个描边对象此前遗漏，导致字母偏细、内孔偏大；第十二轮3条未匹配直线确实对应这批遗漏的描边。

新增embedded_strokes读取子资源自身StyleCluster，按0xCE实例仿射矩阵和scale转换几何。子资源线样式20声明0.25mm线宽，保持纸面宽度，不随16.87倍几何比例放大；原PDF约0.254mm。白色符号笔在本批打印为黑色，按样本证据处理。PDF的lineJoin=1、lineCap=(1,1,1)，对应圆角连接、圆头端点。输出仍完全来自SHA，不借用PDF图像。

四份直线检查分别匹配280、177、189、225条，未匹配数及超阈值线宽差均为零。这仅证明至少3mm的参考描边直线通过0.25mm端点容差及0.15mm线宽容差，不证明曲线、短线、填充和全图完全一致。0212的Wood放大对照图保存于SHA版本核验/wood-reference.png和wood-output.png；可见笔画、内孔和圆角明显接近，仍有约0.1mm级位置偏差。

四份均新增11条嵌入描边，18项回归检查通过；签字和剩余字体排版仍未完成。

## 第十四轮：签字资源与逐图位置核查

新增tools/uae/audit_signature_resources.py，读取4份主SHA、4份template、2份usergraphics，记录流、外部文件引用、SignatureArea字段、源文件SHA256及参考PDF图像对象和纸面坐标。报告为SHA版本核验/signature-resource-audit.json，不修改PDF，也不向转换结果添加外部图像。

四份主SHA的TaggedTxtData/SignatureArea内签字姓名、日期字段全部为空，仅DrawingStatus分别为1、1、16、8；外部图形文件引用只检出Wood Name.sym。流首BMP/PNG/JPEG/TIFF特征仅检出ADNOC BMP，没有在template/usergraphics中找到额外图像流。此项依然不能排除非标准封装或未知编码。

四份参考PDF各有6个图像实例：1个ADNOC Logo、3个修订栏签字、2个专业栏签字。20个签字位置对应8份不同像素摘要；其中两份专业栏签字及一份修订栏签字跨四图复用，其余有所不同。即使图像内容相同，放置坐标也有逐图差异，不能把一张图的签字位置模板直接套在其余图上。

这些证据支持外部出图阶段叠加签字的解释，不作为绝对证明。若采用同版PDF提取方案，必须保留逐图来源、像素摘要和位置，明确它是外部资源补充；此前询问的还原方式尚未得到用户答复。本轮未修改四份核对PDF。

## 第十五轮：纠正字宽字段长度

纠正第十一轮关于其他高度模式采用不同宽度表示的推断：0x2C的+58字宽实际为uint16，+60起是相邻独立字段。此前按uint32读取，在相邻字段非零时产生巨大无效值，错误跳过了图框字体的原生字宽比例。改为所有已观察高度模式统一读取uint16；典型图框字体为920，即92%。

0212的STRESS REVIEW标题横向起点误差由-2.006mm缩小为-0.278mm，SUPPORT SCHEDULE标题由-1.097mm缩小为-0.104mm；竖向NOTICE起点沿页高的误差从3.439mm缩小为1.210mm，仍有字体度量差异。四份唯一匹配文本的宽度误差中位数由约0.242/0.304/0.302/0.248mm降低到0.122/0.163/0.149/0.117mm。统计范围仍仅唯一精确匹配文本，不代表整体还原率。

增加四份真实图框SUPPORT SCHEDULE字体比例0.92的回归约束。18项检查通过，四份PDF已重生成，签字仍待还原方式确认。

## 第十六轮：分区像素检查及漏掉的最新修订号

新增tools/uae/audit_pdf_raster_fidelity.py，200dpi渲染，按纸面0.254mm方形邻域比较双向墨迹覆盖。白底不计分，颜色及语义不计分，近邻错误墨迹可能被容差掩盖，因此不能称为整体还原率。输出raster-fidelity-audit.json和raster-overlays分区差异图，红色为参考图缺少对应输出墨迹，蓝色为输出多出的墨迹。

叠图发现右下角REV.栏漏掉“0”：它绑定/Revision/RevisionRecord[last()]/MinorRev_ForRevise，旧代码只支持修订历史表的复合选择器。此前按唯一文本集合比较因图中其他位置也有0而漏检，证明该指标不能代替位置和重复文本检查。

新增last()选择器，并从所属0x4D记录读取原生格式和对齐属性。动态文本由12项增至13项；四份集成检查要求该最新修订号内容为0，且原生位置位于右下角。PDF交付后另按位置提取，四份均恰好一处0；0212输出约(410.787,287.589)mm，参考约(410.707,287.613)mm。

18项检查通过，四份PDF已重生成。像素分区显示剩余差异主要在标题栏字体排版和签字区；管道区、Wood已较接近参考，但本报告不据此宣称全图完成。

## 第十七轮：两种原始PDF出图方式

新增tools/uae/audit_pdf_text_grid.py，读取字符原点沿文本方向的推进距离，比较96/300/600/1200dpi网格残差，并记录PDF producer/creator及字体资源类型。报告text-grid-audit.json。

0212和0511的producer为GPL Ghostscript 9.06，creator为PScript5.dll Version 5.2.2，使用嵌入CFF的Type1 Times-Roman、Times-Bold、Helvetica等字体。字符推进分别99.65%、99.78%落在600dpi网格的0.01像素容差内；300dpi仅约64.4%、64.7%。600dpi是与观察一致的网格，不排除其整数倍分辨率。

0937和0939的producer为Microsoft: Print To PDF，使用嵌入TTF的Type0 CID字体；字符推进符合600dpi网格的比例仅约1.78%、1.69%。不能把0212/0511的网格规律统一施加于四图，也不能用PDF抽取font_size直接代表真实纵向字号，因为非等比文字矩阵会影响该数值。

此结果不改变此前同版结论，而是说明出图字体替换及驱动量化不同。当前SHA生成器维持同一原生解析路径，本轮没有引入按图号硬编码的打印补偿，也未修改核对PDF。后续排版核验应区分两类原始出图证据，避免为贴合一种驱动而损坏另一种。

## 第十八轮：取消未溢出段落的强制拉伸

原实现对所有有文本框宽度的多行段落都设置SVG textLength，数值来自PyMuPDF标准字体；即使没有溢出，也强制覆盖浏览器实际所选Windows字体的字宽和字距。现在只有估算宽度超出声明文本框时才执行压缩，正常段落沿用所选字体自身度量。

0212的LONG TERM - EXECUTE STAGE宽度差从约2.011mm减小到1.625mm，起点偏差从-0.985mm减小到-0.791mm。该修正只消除一项不必要的字体拉伸，没有解决不同出图驱动的全部度量差异。四份PDF、文字报告和像素差异叠图已更新，18项检查通过；签字仍未补入。

## 第十九轮：动态修订日期文本框

动态绑定的0x4D记录同样携带文本框宽度：变换后+40的double，单位米。此前bound_text只保留内容与坐标，丢掉此字段；日期格式中的paragraph_alignment=0x100因此未能生效。

现从动态绑定所属记录读取宽度，验证范围后按原生居中对齐。两个日期框分别约15.385mm、14.741mm，不按日期内容设定偏移。0212/0511的08-MAY-2026横向误差由约-1.025mm变为+0.067mm，28-AUG-2026由约-0.898mm变为-0.150mm；0937/0939分别为+0.140mm、-0.076mm。

四份真实样本增加两个动态日期框宽度的回归验证。18项检查通过，四份PDF和文字对照报告已更新。修订历史表字体仍沿用之前校准的2.25mm，未声称全部动态文本排版参数完成解码。

## 第二十轮：重复文字位置与单行文本框

文字对照工具新增逐次出现核对：同内容、同页、5mm范围内按原点距离贪心一对一配对，保留数量差、未匹配位置和超过1mm的偏差。它不是重复标签语义的唯一对应证明，但避免只看文本集合而漏掉右下角修订号等问题。四份分别匹配331、268、286、330个出现位置；仅剩PT / MT被PDF合并/拆分造成的一对二span差异，没有发现其他数量差异。

该检查定位剩余两条竖向NOTICE的约1.2mm偏差。它们的有效内容为单行，仍有SHA声明的文本框宽度49.120mm和39.697mm；原代码只压缩多行溢出，漏掉这些单行框。现所有有声明宽度的文本都执行溢出检查，同时把原生字宽比例计入最终纸面宽度；未溢出的文字继续使用自然字距。

两条竖向说明的位置偏差降至约0.10—0.16mm；0212第二条宽度差降到约0.015mm（各条具体数据见报告），四份逐次出现匹配中已没有大于1mm的原点距离差。此阈值不评价文字轮廓、每字间距或宽度，也不覆盖签字。18项检查通过，PDF、文字报告和像素叠图已更新。

## 第二十一轮：独立签字补充审阅成果

为使外部资源方案具体可审阅，新增workflow/create_signature_review.py，在独立的SHA转PDF_签字补充核对目录制作四份补充版；纯SHA输出不变。签字补充资源目录保留PNG、manifest.json和review-validation.json，清楚标记pure_sha_decode=false及reference_pdf_image来源。此步骤是本地核对草稿，不替换默认纯SHA解析方式。

每图3个修订栏签字、2个专业栏签字。图像保留PDF软蒙版，依据原PDF旋转矩阵换算纸面位置；keep_proportion=false保留源文件实际非等比缩放，不猜测统一签字模板。只支持当前已验证的正向轴对齐图像矩阵，其他旋转、镜像、剪切报错。

四份均通过单页A3、PDF可读性、6个图像实例（含ADNOC）、5处签字位置小于0.001pt误差的检查。两类签字区在200dpi/0.254mm容差下双向墨迹覆盖均为1.0，这不等于全图逐像素一致。输入SHA、原PDF、纯SHA PDF哈希均保持不变，补充版输出目录仅4个PDF。0212整页已做视觉检查。该成果明确是来源可追踪的外部图像补充，不能宣称签字已从SHA中解出。
