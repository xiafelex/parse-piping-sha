# 阿联酋POD格式研究与验证记录

证据范围：四组NativeFiles，序列化版本字符串均为`6.0.0.92`。下面是样本验证的布局，不是厂商公开二进制规范。
所有offset/end均为`PODFile`逻辑流偏移，end为不含端点；不是整个OLE文件偏移。

## 容器与对象边界

外层为OLE/CFB，文件头`D0 CF 11 E0 A1 B1 1A E1`，四个样本均只有`PODFile`流。
流长依次为224424、107095、126459、167430字节。

```text
00 50 1A A1       对象开始
uint32 LE        tag（可能含版本语义，不能统一称为对象类型）
payload          普通数据段、子对象交替出现
FF 50 1A A1       对象结束
```

四个样本全部配对，无游离结束标记，根对象恰好覆盖完整流；最大嵌套深度9（根深度0）。
这是经语义、数值和图形重复交叉验证的边界，但尚未发现正式的转义机制规范；对其它版本或包含标记碰撞的文件，应拒绝而不是猜测。
开始标记后的tag值在不同上下文重复出现，不能仅凭tag分配全局类名。

根对象tag=5，包括版本串、控制字段、文档GUID、POD属性集合、管线集合及尾部集合。
本批每份仅一条管线。管线对象tag=7，包含名称、控制字段、起点数据及15个子集合。
按当前子集合序号，已辨认出：线样式、填充样式、字体、图层、全图图形、管线属性、构件属性定义、材料、构件/关系、汇总及空集合。
未确认的控制值与集合保留字节及对象偏移。

## 字符串和数值类型

字符串：`uint32LE allocated_byte_length`后为UTF-16LE字符串，包含终止零与可能的零填充。
例如根版本串分配18字节；不是按Python字符数直接读取。读取器检查长度、终止符和剩余字节。

属性有两种结构：

1. 完整定义：槽位、属性ID、标记、属性名、显示名、分类码、值类型、布尔/控制位、约束XML，可附带值。
2. 简短实例：槽位uint32、属性ID uint32、标记uint8、类型码uint16、值、presence uint8。

当前实际解出的类型码：8=UTF-16字符串、3=int32、5=IEEE754 float64、0=空值（仍带空字符串储存）。
类型编号与COM VARIANT相似，但没有据此假定其它VARIANT类型也被支持。
float64用于螺栓尺寸、角度、重量、坐标等；实际字段归属由属性定义或上下文确认。

同一属性ID在不同集合可能重名冲突，例如113在管线属性中是ATTRIBUTE43，在材料属性中是BOLT-LENGTH。
解码器不把冲突ID当全局唯一。部分继承构件属性按槽位给出候选名称，并标记证据级别；308个可与PCF对照的构件属性值全部匹配。

## 构件、端口和连接

构件对象含：POD内部GUID、UCI、构件类别码、材料GUID、端口集合、腿段集合、属性、图形、附加对象。
PCF的UCI与POD内部GUID不同，二者不能混用。0511的两个PIPE共享同一UCI，但POD有两个独立对象及各自端口。
集合中还含tag=2的关系记录，记录自身GUID、源对象GUID、源端口、目标GUID，以及可选目标端口；目标可能是附加对象，不能都当成物理管段连接。

端口头布局已在232个端口上完整读取：

```text
string name              Run_1 / Run_2 / Centre_1 / Centre_2 ...
uint8 centre_flag
float64 bore
uint32 bore_unit_code
string end_preparation
string peer_port
string peer_object_guid
int32 drawing_x
int32 drawing_y
uint8 drawing_flag
嵌套XYZ对象：三个轴对象，每轴 uint32 mode + float64 value + float64 extra
```

XYZ是工程坐标，本批单位毫米；二维点采用纸面整数坐标，和SHA纸面米坐标之比为1000000。
本批POD工程坐标有0.01mm级舍入，故与PCF的0.001mm数据采用0.011mm距离容差核对。

227/232个端口直接与同UCI的PCF点一致；余下5个均记录在审计中，不强行调整：

- 0937、0939各一个螺栓中心，与PCF显式MASTER-COMPONENT-IDENTIFIER所指构件的CENTRE-POINT一致，而非BOLT CO-ORDS。
- 0511一个螺栓中心同样与仪表主构件中心一致。
- 0511偏心异径管另有Centre_1/Centre_2辅助点；PCF只给两个端点，没有同角色中心点可直接比对。

## 绘图记录

图形组含图层ID、局部编号、图元个数；每个子图元前有uint32图元类型。最后子对象之后还可能有控制字段，不能误认为另一个图元类型。

| 图元码 | 已解布局 | 当前验证边界 |
|---|---|---|
| 3 | 4×int32端点 + uint32样式引用 | 974条全部与SHA一致 |
| 6/7 | 样式、填充码、顶点数、int32二维点数组 | 轮廓已解；部分填充语义仍需确认 |
| 1 | 中心int32×2、半径int32、样式、填充码 | 圆形/焊点记录；精确线型未全解 |
| 8 | 长度字符串、整数XY/字宽/字高、字体、样式、旋转等 | 795条文字记录；对齐、字宽控制仍在验证 |
| 0 | 8×int32：中心、半径对、旋转、起角、带符号扫角、样式 | 4条圆弧的中心、半径、角度与方向均已独立匹配SHA |

POD纸面单位是0.001mm。字体表含Arial、Arial Bold、Courier New、Times New Roman；图层表含PIPE、FITTINGS、DIMTEXT、MATLIST等。
图形组在构件对象内部的嵌套关系，直接给出POD图元→POD对象→UCI关联。

## 与SHA的实际对应

本项目SHA线记录头为`18 00 32 00 00 00`，之后有uint32图元引用、uint32所有者引用、uint32样式引用、uint16零、uint32标志，再接4个float64坐标。
已找到超过65535的引用（如74500），原蓝星部分uint16+零高位识别会漏掉这些记录，因此在uae中增加完整32位读取。
`SHA坐标×1000000=POD整数坐标`，允许端点交换后四份POD的416/152/159/247条直线全部精确匹配。
重叠线段可能对应多个SHA记录，输出保留全部候选，不伪造唯一UCI绑定。

圆弧角度单位为0.001度，第二角度是扫角，不是终点角。例如0212首条为起角60.019度、扫角59.962度，终点119.981度；另一条起角-60.018度、扫角-119.982度，终点-180度。与SHA的弧度值和方向标记独立一致。四条都是圆弧（两半径相同，旋转0）；不将其泛化为已验证任意椭圆弧。

SHA的Sheet6含主图和动态文字，另有Sheet39817、模板/用户图形和修订XML等信息；这些不应全部视为POD固有内容。
POD有工程端口、关系、属性定义和加工结构；SHA适合最终图形、修订、图框及后期编辑信息。二者有相同图元，但不可互相无损替代。

## 无损回写与完整解码的区别

无损JSON树按对象和直接数据段交替保存，未知数据用base64保留；重新编码后逻辑流逐字节一致。
CFB的原有目录、FAT和扇区余留字节作为容器模板保留，只回填逻辑流字节，整个POD文件哈希亦一致。
olefile.write_stream会清零最后扇区的余留字节，本批文件因此不能用它验证全文件字节一致性。
这不是POD语义编辑器，也不是不依赖模板的通用OLE写入器。

尚未完成：所有控制字段的业务命名、完整材质/汇总关系、非圆形椭圆弧验证、精确文字排版与线型、SHA模板和嵌入图形的变换关系，以及不同POD版本适配。
完整语义解码标记保持false。每个未解字段仍可从对象树中追回，不以填零或删除方式掩盖。
